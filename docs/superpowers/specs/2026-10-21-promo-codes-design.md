# Promo codes (sub-project 4b) — design

Date: 2026-10-21. Parent spec: `2026-10-01-minecraft-donation-shop-design.md` (§7.2, §7.5, §9.1, §11.5, §13). Builds on 4a (`2026-10-16-checkout-design.md`).

## Intent

The owner hands out short text codes (`ASF14`) in Discord, streams and seasonal promos. A player types the code in the checkout modal and immediately sees the order get cheaper. The moment the total changes is the reward, so it is animated with care. The owner creates and manages codes in the admin without touching the database.

## Goals

- Player enters a code at checkout, sees the discount and the new total before paying.
- The server is the only authority: prices and discount are recomputed on `POST /api/orders`; the use is reserved atomically, so a code with `maxUses = 1` is used exactly once even under concurrency.
- Admin CRUD for codes, with a generate button, usage counters and soft delete.
- Orders keep the code and discount forever, even after the code is deleted.

## Non-goals

- Per-player limits ("once per nick/email").
- Bulk generation of many codes.
- More than one code per order; stacking.
- Automatic discounts without a code.
- Refund handling of promo usage (refunds arrive in sub-project 5).

## Anti-goals

- A client-computed price ever reaching Stripe.
- A code with a use limit being over-redeemed by parallel checkouts.
- Deleting a code breaking an order's history in the admin.

## Player flow (web)

Agreed with the owner:

1. In the checkout modal's Order summary (`apps/web/src/features/checkout/components/order-summary.tsx`), below the lines, a collapsed link "Have a promo code?". Clicking it reveals an input and an "Apply" button. Input is case-insensitive (`asf14` = `ASF14`), trimmed.
2. Apply calls `POST /api/promo/validate` with the code, the cart lines and the currency. On success the input is replaced by a chip `ASF14 ×` (× removes the code), a "Discount −€2.40" row appears in the totals, and the total animates to the new value. The same animated total is used in the phone `PayBar` and in the Pay button label.
3. On failure a short reason under the input: not found, not started yet, expired, used up, does not apply to these items, fixed amount in another currency. (Disabled and deleted codes read as "not found".)
4. When the cart or the currency changes while a code is applied, the client re-validates; if the code no longer applies it is removed and the reason is shown.
5. `POST /api/orders` takes an optional `promoCode`. If it fails there (e.g. used up between Apply and Pay) no order is created; the response is an error with the reason, the client removes the code and shows the reason; the player can pay again without it.
6. After payment the player sees the discount too: the receipt email (`apps/api/src/mail`) and the public order page `/order/:publicId` show a "Promo code ASF14: −€2.40" row between the lines and the total (agreed with the owner). The `PublicOrder` contract gains `subtotalMinor`, `discountMinor` and `promoCode`; EN/PL strings for mail and web.
7. One code per order. The discount never takes the total below the Stripe minimum for the currency (EUR 50 minor, PLN 200 minor); it is capped instead.

Visual design of the summary changes (reveal, chip, discount row, number animation) is done with the `impeccable` skill during implementation, using the existing web tokens and Motion (already a dependency). The owner reviews it afterwards. Must respect `prefers-reduced-motion` (no rolling digits, instant change) and announce the new total to screen readers (polite live region).

## Admin flow

Agreed with the owner:

1. Rail item "Promo codes", page `/promo-codes`, EN/PL strings.
2. `DataTable` columns: code, discount (`15%` or `€5.00`), uses `3 / 100` (or `3 / ∞`), period, status as dot + label: active, scheduled, expired, used up, disabled. `RowMenu`: edit, disable/enable, delete.
3. Create/edit form:
   - code: typed by hand, or generated by a dice button next to the input. Generation animates like a split-flap board: the field starts from a placeholder pattern (`AAAAA000`) and each character flips through random characters before settling on the result (e.g. `BASFZ931`). Format: 5 letters + 3 digits, alphabet without look-alikes (no `O`, `I`, `0`, `1`) _(alphabet: my call)_. Reduced motion → instant. Stored upper-case; unique among non-deleted codes; `A–Z 0–9`, 3–32 chars _(length bounds: my call)_.
   - kind: percent (1–100) or fixed amount + currency (EUR or PLN).
   - max uses: empty = unlimited.
   - starts at / ends at: both optional (date-time pickers; the popover/calendar primitives already exist).
   - scope: whole shop, or selected categories and/or products (a line is eligible if its product is selected or its category is selected).
   - enabled toggle.
4. Once a code has been used (`usedCount > 0` or any order references it), code text, kind, value, currency and scope are locked (agreed with the owner): the form shows them disabled with a one-line hint ("create a new code for a different discount"), and the update endpoint rejects changes to them with a `promo_locked` error. Still editable: `maxUses` (not below `usedCount`), start/end dates, enabled.
5. Delete is a soft delete (`deletedAt`): the code disappears from the list and stops working; orders keep the code text and discount. A deleted code's text can be reused by a new code _(my call)_.
6. The admin order detail shows the applied code and the discount.
7. Every write goes to the audit log, like the catalog.
8. Permission: `promo.write` guards the page and all endpoints (as in the parent spec; matches `catalog.write` guarding catalog reads). Added to `PERMISSIONS` and the `ADMIN` system role. _(Earlier I proposed a separate `promo.read`; dropped as unnecessary — my call.)_

## Data model

`promo_codes`:

- `id`, `code` (stored upper-case), `kind` (`PERCENT` | `FIXED`), `value` Int (percent 1–100, or minor units), `currency` Currency? (required iff `FIXED`), `maxUses` Int?, `usedCount` Int default 0, `startsAt`/`endsAt` DateTime?, `isActive` Boolean default true, `deletedAt` DateTime?, `version` Int (optimistic locking, like the catalog), timestamps.
- Unique index on `code` where `deletedAt IS NULL` (partial index via raw SQL in the migration). Codes are stored upper-case, so plain uniqueness is case-insensitive.
- Scope: join tables `promo_code_categories` and `promo_code_products`. Both empty = whole shop.

`orders`: add `promoCodeId` String? (FK, `onDelete: Restrict` — soft delete never removes the row) and `promoCode` String? (snapshot of the code text). `discountMinor` and `subtotalMinor` already exist.

## Discount rules

Pure function in `apps/api/src/orders/` next to `order-pricing.ts`, unit-tested:

- Eligible subtotal = sum of priced lines in scope. Zero → `not_applicable`.
- `PERCENT`: `floor(eligible × value / 100)`.
- `FIXED`: `min(value, eligible)`; currency must equal the order currency, else `wrong_currency`.
- Cap: `discount ≤ subtotal − stripeMinimum(currency)`; if that is ≤ 0 the code yields no discount → `not_applicable` _(my call: rather than silently applying zero)_.
- Validity checks, in order: exists and not deleted and enabled (`not_found`), `startsAt ≤ now` (`not_started`), `now < endsAt` (`expired`), `usedCount < maxUses` (`used_up`), then scope/currency/amount.

`/api/promo/validate` and `/api/orders` use the same function; validate never reserves.

## Reservation lifecycle

- `POST /api/orders`, inside the transaction that creates the order: `UPDATE promo_codes SET usedCount = usedCount + 1 WHERE id = $1 AND deletedAt IS NULL AND isActive AND (maxUses IS NULL OR usedCount < maxUses)`; 0 rows → `used_up`, transaction rolls back, no order. The order transaction already wraps the gateway call (15 s timeout), so the `UPDATE` runs as the **last** statement, after `createSession`: the code's row is locked only for the commit, not for the Stripe round-trip, and a popular code does not serialize checkouts _(my call)_. If it loses the race, the Stripe session already created is orphaned and expires on its own (its webhook names an unknown session and is logged, as today).
- Order goes `EXPIRED` (the `failed`/expired webhook in `payment-events.service.ts`) → in the same transaction, if the status update changed a row and the order has a `promoCodeId`, `usedCount - 1` (never below 0).
- Late payment of an `EXPIRED` order (the existing `EXPIRED → PAID` path) → `usedCount + 1` unconditionally, even past `maxUses`: the money is taken, the discount is honored _(my call)_.
- `usedCount` therefore counts PENDING + PAID orders, which is what "uses" shows in the admin.

## Payments

`SessionRequest` gains `discountMinor`. Stripe gateway: when > 0, create a one-off coupon (`amount_off`, the order currency, `duration: once`, `max_redemptions: 1`, name = the code) and pass it in `discounts`; Stripe's `amount_total` then equals `order.totalMinor`, which the webhook already checks. Fake gateway shows the discount line and charges the discounted total. Line items stay at full unit prices.

## API surface

- Public `POST /api/promo/validate` (`@AllowAnonymous`): body `{code, currency, lines}` (same line shape as orders); response `{ok: true, code, discountMinor, subtotalMinor, totalMinor}` or `{ok: false, reason}`. Rate limit 20/min per IP (parent spec §7.5). No Turnstile.
- `POST /api/orders`: optional `promoCode`; new error `{error: 'promo', reason}`.
- Admin `/api/admin/promo-codes`: list (with status and usage), get, create, update (with `version`), enable/disable, delete (soft). Documented in `apps/api/src/openapi/` (operationId, tags, summary, description, responses); admin RTK Query regenerated.
- Contracts (schemas, reason codes) in `@shop/shared` (new `promo.ts`, extending `orders.ts`).

## Tests

- Unit: discount function (percent rounding, fixed cap, minimum cap, scope by category/product, all reasons); code generator format.
- Integration (`*.int-spec.ts`, Testcontainers): 20 parallel orders on a code with `maxUses = 1` → exactly one order created (parent spec §13); expiry releases a use; late payment re-takes it; soft-deleted code is rejected and its text reusable.
- Web: summary applies/removes a code, shows reasons, re-validates on cart change; i18n key-set parity (EN/PL) for web and admin.
- Admin: messages parity; form validation.
- E2E: apply a code at checkout with the fake gateway and see the discounted total on the fake payment page; admin creates a code.
